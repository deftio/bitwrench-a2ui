# Using with LLMs

A2UI is designed to be generated by language models. A model needs to know the catalog it may use, the message format, and how to respond to actions. This page explains a simple direct approach and the project's LLM sandbox page.

## Two ways to generate A2UI

There are two common setups:

* **With an agent SDK** - Google's A2UI agent SDKs (TypeScript, Python, Dart) build prompts from catalogs, let the model write a compact format (A2UI Express), compile it to standard v1.0 JSON, and validate it before sending. This is the robust choice for production agents. The renderer only ever sees standard JSON, so it works with any of them.
* **Direct JSON** - prompt the model to output v1.0 envelopes as JSON Lines. Simpler, good for prototypes and demos, and what the sandbox page does.

## A direct prompt

The core of a direct prompt:

```text
You build user interfaces with the A2UI v1.0 protocol. Reply with JSON Lines only:
one A2UI message per line, no prose, no code fences.

Start with a createSurface message (surfaceId "main", catalogId
"https://a2ui.org/specification/v1_0/catalogs/basic/catalog.json") carrying the
components and the dataModel. Components are a flat list; exactly one has id "root";
containers refer to children by id.

Bind values with {"@path": "/json/pointer"}. Inputs (TextField, CheckBox,
ChoicePicker, Slider, DateTimeInput) must bind their value to a data model path.
Buttons send actions: {"event": {"name": "...", "context": {"key": {"@path": "/..."}}}}.

Available components and properties: <the basic catalog's component list>
```

Include the catalog. The basic catalog document has an `instructions` field and a description for every property; the sandbox page builds its prompt from them. When the user clicks a button, send the model the resulting `action` message as the next user turn and ask for the updated UI.

## Handling imperfect output

Models make mistakes. The renderer helps you notice:

* **Errors are explicit** - invalid messages produce `error` envelopes (and `onDiagnostic` calls) with a JSON path. Feed them back to the model and ask for a corrected message.
* **Nothing unsafe renders** - a bad message cannot run code or inject HTML (see [Security](security.md)).
* **Streaming is tolerant** - use `validation: 'relaxed'` and `receiveStream()` so components render as lines arrive.

## The LLM sandbox page

The project site has a sandbox page (`pages/llm.html`) where you paste an API key, describe a UI, and watch a model build it live:

* **Providers** - Claude (Anthropic), Gemini (Google) and OpenAI, called directly from your browser. There is no server in between.
* **Prompt** - built from the basic catalog document, as above.
* **Loop** - the model's JSON Lines render as they arrive; clicking a button sends the action back as the next turn.
* **Inspection** - the same panes as the playground show the wire messages, data model, TACO and diagnostics, so model mistakes are visible.
* **Keys** - held in the page's memory only (never written to browser storage, gone on reload), sent only to the provider you choose, and cleared with one button. Use a restricted or development key. Anthropic requires its `anthropic-dangerous-direct-browser-access` header for direct browser calls; the page sets it, because the call is the user's own key in the user's own browser.

The page is a demo: results vary with the model and the prompt.
